Chapter 01

Application Design & Build

Exam weight · 20%

The CKAD is a hands-on exam: no multiple choice, just a terminal, a set of clusters, and tasks like "create a CronJob that runs every 5 minutes and keeps 2 successful jobs" or "add a sidecar that tails the app's log file". This first domain covers the raw material of every Kubernetes application: the container image, the workload controller that runs it, how several containers cooperate inside one Pod, and where data lives when the container restarts.

1.1 Container Images

Kubernetes never builds images — it pulls them. But the exam expects you to be able to build, tag and export an image from a Dockerfile using whatever runtime CLI is on the node (docker or podman, their syntax is nearly identical).

# Multi-stage build: compile in a fat image, ship a thin one
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download            # cached layer while deps don't change
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

FROM gcr.io/distroless/static:nonroot
COPY --from=build /app /app
USER nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
# Build, tag, inspect, export
podman build -t myapp:v1 .
podman tag myapp:v1 registry.example.com/team/myapp:v1
podman images
podman save myapp:v1 -o myapp-v1.tar          # exam favourite: "save the image as a tarball"
podman push registry.example.com/team/myapp:v1
podman run -d --name test -p 8080:8080 myapp:v1
ENTRYPOINT/CMD vs command/args

In a Pod spec, command overrides the image's ENTRYPOINT and args overrides CMD. Set only args and the image's entrypoint still runs with your arguments. On the command line, kubectl run x --image=busybox -- sleep 3600 sets args; add --command to set command instead.

Tags, digests and imagePullPolicy

PolicyBehaviourDefault when
AlwaysAsk the registry every time a container starts (cheap if layers are cached)Tag is :latest or omitted
IfNotPresentPull only if the image isn't on the nodeAny other tag or a digest
NeverUse the local image or fail with ErrImageNeverPullNever a default
Production habit: pin by digest (nginx@sha256:…) or an immutable tag. A mutable tag means two Pods of the same Deployment can run different code.

1.2 Pods & Workload Resources

A Pod is the unit of scheduling: one or more containers sharing a network namespace (same IP, talk over localhost), optionally sharing volumes, always co-located on one node. You almost never create bare Pods in production — a controller creates them for you and replaces them when they die.

apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web
    tier: frontend
spec:
  containers:
  - name: nginx
    image: nginx:1.27
    ports:
    - containerPort: 80
    env:
    - name: MODE
      value: "production"
  restartPolicy: Always        # Always | OnFailure | Never

Choosing a controller

ResourceUse forKey property
DeploymentStateless apps (web, APIs)Manages ReplicaSets; rolling updates & rollback
ReplicaSetRarely directlyKeeps N identical Pods matching a selector
StatefulSetDatabases, quorum systemsStable names (db-0, db-1), ordered start, per-Pod PVC via volumeClaimTemplates
DaemonSetNode agents (log shippers, CNI, monitoring)Exactly one Pod per (matching) node
JobRun-to-completion batch workRetries until N successes
CronJobScheduled batch workCreates a Job on a cron schedule
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api                 # must match template labels — immutable after creation
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: myapp:v1
        ports:
        - containerPort: 8080
Selector mismatch: if spec.selector.matchLabels doesn't match spec.template.metadata.labels, the API server rejects the Deployment. And the selector is immutable — changing it means deleting and recreating. 
# Never write these from scratch — generate, then edit
kubectl run web --image=nginx:1.27 --labels=app=web,tier=frontend --port=80 --dry-run=client -o yaml > pod.yaml
kubectl create deployment api --image=myapp:v1 --replicas=3 --port=8080 --dry-run=client -o yaml > deploy.yaml

# A DaemonSet has no generator: create a Deployment, then edit
#   kind: Deployment -> DaemonSet, delete replicas, strategy and status

StatefulSet in brief

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless     # headless Service gives db-0.db-headless DNS names
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:        # one PVC per replica: data-db-0, data-db-1, ...
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi

1.3 Jobs & CronJobs

A Job runs Pods until a given number complete successfully. The Pod's restartPolicy must be Never or OnFailure — Always makes no sense for something that is supposed to finish.

apiVersion: batch/v1
kind: Job
metadata:
  name: pi
spec:
  completions: 5               # need 5 successful Pods in total
  parallelism: 2               # run at most 2 at a time
  backoffLimit: 4              # give up after 4 failed retries
  activeDeadlineSeconds: 120   # hard wall-clock limit for the whole Job
  ttlSecondsAfterFinished: 300 # garbage-collect the Job 5 min after it ends
  template:
    spec:
      restartPolicy: Never     # Never: new Pod per failure; OnFailure: restart container in place
      containers:
      - name: pi
        image: perl:5.34
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
FieldMeaning
completionsSuccessful Pods required (default 1)
parallelismMax concurrent Pods (default 1)
backoffLimitRetries before the Job is marked Failed (default 6, exponential delay)
activeDeadlineSecondsJob-wide deadline; takes precedence over backoffLimit
completionMode: IndexedEach Pod gets JOB_COMPLETION_INDEX 0..N-1 — for sharded work
apiVersion: batch/v1
kind: CronJob
metadata:
  name: report
spec:
  schedule: "*/5 * * * *"          # min hour day-of-month month day-of-week
  concurrencyPolicy: Forbid        # Allow | Forbid (skip if still running) | Replace
  startingDeadlineSeconds: 60      # skip a run if it can't start within 60s of its slot
  successfulJobsHistoryLimit: 2
  failedJobsHistoryLimit: 1
  suspend: false
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report
            image: busybox:1.36
            command: ["sh", "-c", "date; echo generating report"]
kubectl create job pi --image=perl:5.34 -- perl -Mbignum=bpi -wle 'print bpi(100)'
kubectl create cronjob report --image=busybox:1.36 --schedule="*/5 * * * *" -- sh -c 'date'

# Trigger a CronJob manually (great for verifying your answer)
kubectl create job report-manual --from=cronjob/report

kubectl get jobs -w
kubectl logs job/pi
Exam tip: generators don't expose completions, parallelism or the history limits. Generate with --dry-run=client -o yaml, then add the fields by hand — kubectl explain cronjob.spec lists them if you forget a name.

1.4 Multi-Container Pods

Containers in one Pod share the network namespace and can share volumes. That makes it natural to split a concern out of the main container without changing its code. Four patterns cover nearly every exam question:

PatternWhat it doesExample
Init containerRuns to completion before app containers start, in orderWait for a DB, fetch config, run migrations
SidecarRuns alongside the app for its whole life, extending itLog shipper, proxy, file syncer
AmbassadorProxies the app's outbound connectionsApp talks to localhost:6379; ambassador routes to the right Redis
AdapterTransforms the app's output into a standard formatConvert custom logs/metrics to Prometheus format
apiVersion: v1
kind: Pod
metadata:
  name: app-with-helpers
spec:
  initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ["sh", "-c", "until nslookup db; do echo waiting; sleep 2; done"]

  # Native sidecar (stable since v1.33): an init container with restartPolicy: Always
  # starts before the app, keeps running, and is stopped after the app on shutdown.
  - name: log-shipper
    image: busybox:1.36
    restartPolicy: Always
    command: ["sh", "-c", "tail -F /var/log/app/app.log"]
    volumeMounts:
    - name: logs
      mountPath: /var/log/app

  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "while true; do date >> /var/log/app/app.log; sleep 5; done"]
    volumeMounts:
    - name: logs
      mountPath: /var/log/app

  volumes:
  - name: logs
    emptyDir: {}
Classic vs native sidecars

The classic sidecar is just a second entry in containers. It works, but there's no ordering: it may start after the app, and in a Job it keeps the Pod alive forever after the main container exits. The native sidecar (an initContainers entry with restartPolicy: Always) fixes both. On the exam, use whichever the task describes — if it says "add a container", the classic form is fine.

# Work with a specific container in a multi-container Pod
kubectl logs app-with-helpers -c log-shipper
kubectl exec -it app-with-helpers -c app -- sh
kubectl get pod app-with-helpers -o jsonpath='{.spec.containers[*].name}'
Init containers block: while an init container hasn't finished the Pod shows Init:0/2; if it keeps failing, Init:CrashLoopBackOff. Read its logs with kubectl logs pod -c <init-name>.

1.5 Volumes & Persistent Storage

A container's filesystem is ephemeral — it's reset on every restart. Volumes give it storage with a different lifecycle: tied to the Pod (emptyDir), to the node (hostPath), or independent of both (a PersistentVolume).

VolumeLifetimeTypical use
emptyDirPod (survives container restarts)Scratch space, sharing files between containers; medium: Memory for tmpfs
hostPathNodeNode agents reading /var/log; avoid for apps
configMap / secretObjectConfig files (Chapter 4)
persistentVolumeClaimIndependentDatabases, uploads — anything that must survive Pod deletion

PV, PVC and StorageClass

The split is about roles: an admin (or a provisioner) supplies PersistentVolumes; a developer asks for storage with a PersistentVolumeClaim; Kubernetes binds a claim to a volume that satisfies its size, access mode and storage class. With a StorageClass and dynamic provisioning, the PV is created on demand.

apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-data
spec:
  capacity:
    storage: 1Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain   # Retain | Delete
  storageClassName: manual
  hostPath:
    path: /mnt/data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  storageClassName: manual       # must match the PV (or omit to use the default class)
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 500Mi             # PV must be at least this big
---
apiVersion: v1
kind: Pod
metadata:
  name: uses-pvc
spec:
  containers:
  - name: app
    image: nginx:1.27
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data
Access modeShortMeaning
ReadWriteOnceRWORead-write by a single node (several Pods on that node are OK)
ReadOnlyManyROXRead-only by many nodes
ReadWriteManyRWXRead-write by many nodes (NFS, CephFS, EFS…)
ReadWriteOncePodRWOPRead-write by a single Pod
PVC stuck in Pending? kubectl describe pvc tells you why. Usual suspects: storageClassName mismatch, no PV big enough, access mode not offered, or a WaitForFirstConsumer class that waits for a Pod to use the claim before binding.
Key Takeaways — Chapter 1
  • command overrides ENTRYPOINT, args overrides CMD
  • Build/tag/save images with docker or podman; :latest implies Always
  • Deployment for stateless, StatefulSet for identity + storage, DaemonSet per node
  • Jobs: completions, parallelism, backoffLimit; restartPolicy is Never or OnFailure
  • CronJob concurrencyPolicy Forbid/Replace; test with create job --from=cronjob/x
  • Init containers run first, in order; native sidecars are init containers with restartPolicy Always
  • emptyDir lives with the Pod; PVCs bind to PVs by class, size and access mode
  • Generate YAML with --dry-run=client -o yaml, then edit
Chapter 02

Application Deployment

Exam weight · 20%

Getting a workload running is half the job; changing it safely is the other half. This chapter covers how a Deployment replaces old Pods with new ones, how to fake blue-green and canary releases with nothing but labels, how to scale, and the two packaging tools the exam expects you to drive: Helm and Kustomize.

2.1 Rolling Updates & Rollbacks

Every change to a Deployment's spec.template (image, env, resources, labels…) creates a new ReplicaSet. The Deployment controller then scales the new one up and the old one down according to the strategy. Changing replicas alone does not trigger a rollout.

spec:
  replicas: 4
  strategy:
    type: RollingUpdate          # default; the other option is Recreate
    rollingUpdate:
      maxSurge: 1                # at most 4+1 = 5 Pods during the rollout
      maxUnavailable: 0          # never drop below 4 ready Pods
  minReadySeconds: 10            # a new Pod must stay Ready 10s before it counts
  revisionHistoryLimit: 5        # old ReplicaSets kept for rollback
StrategyBehaviourWhen
RollingUpdateGradual replacement bounded by maxSurge / maxUnavailable (defaults 25% / 25%)Default; zero-downtime if readiness probes are right
RecreateKill all old Pods, then start new onesApp can't run two versions at once (schema locks, singleton)
# Trigger a rollout
kubectl set image deployment/api api=myapp:v2
kubectl annotate deployment/api kubernetes.io/change-cause="upgrade to v2"   # shows in history

# Watch and inspect
kubectl rollout status deployment/api
kubectl rollout history deployment/api
kubectl rollout history deployment/api --revision=2     # full template of revision 2

# Undo
kubectl rollout undo deployment/api                     # back to the previous revision
kubectl rollout undo deployment/api --to-revision=1

# Batch several edits into one rollout
kubectl rollout pause deployment/api
kubectl set image deployment/api api=myapp:v3
kubectl set resources deployment/api -c api --limits=cpu=500m,memory=256Mi
kubectl rollout resume deployment/api

# Re-create all Pods with the same spec (e.g. to pick up a changed ConfigMap)
kubectl rollout restart deployment/api
--record is gone: older guides use kubectl set image … --record. It's deprecated; set the kubernetes.io/change-cause annotation instead.

2.2 Blue-Green & Canary

Kubernetes has no built-in blue-green or canary object — but a Service routes to whatever Pods match its selector, and that's enough to build both.

Blue-green: switch the selector

# Two full Deployments side by side
#   web-blue:  labels app=web, version=blue   (current)
#   web-green: labels app=web, version=green  (new, fully scaled, tested)
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
    version: blue              # flip to green for an instant cut-over
  ports:
  - port: 80
    targetPort: 8080
kubectl patch service web -p '{"spec":{"selector":{"app":"web","version":"green"}}}'
# Rollback = patch it back to blue. Delete web-blue once you're confident.

Canary: share a label, split by replica count

# Service selects only app=web, so it spreads traffic across BOTH Deployments.
#   web-stable: replicas 9, labels app=web, track=stable, image myapp:v1
#   web-canary: replicas 1, labels app=web, track=canary, image myapp:v2
# => roughly 10% of requests hit v2.
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 8080
# Promote gradually, then retire the old version
kubectl scale deployment web-canary --replicas=5
kubectl scale deployment web-stable --replicas=5
kubectl set image deployment/web-stable app=myapp:v2
kubectl delete deployment web-canary
Exam pattern: "Route ~20% of traffic to the new version, keep 5 Pods total" → 4 stable + 1 canary, both carrying the label the Service selects. Verify with kubectl get endpoints web — you should see 5 IPs.

2.3 Scaling & Autoscaling

kubectl scale deployment api --replicas=6
kubectl scale deployment api --current-replicas=6 --replicas=3   # only if currently 6

# HorizontalPodAutoscaler: keep average CPU at 70% of requests, between 2 and 10 Pods
kubectl autoscale deployment api --cpu-percent=70 --min=2 --max=10
kubectl get hpa -w
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
HPA shows <unknown>? Utilization is measured against requests. If the containers don't set resources.requests.cpu, or metrics-server isn't installed, the HPA can't compute anything.

2.4 Helm

Helm is a package manager: a chart is a bundle of templated manifests plus default values.yaml; installing it creates a release, and each upgrade bumps the release's revision. On the exam you'll consume charts, not write them.

# Repositories
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo nginx
helm search repo bitnami/nginx --versions      # list chart versions

# Inspect before installing
helm show values bitnami/nginx | less
helm template web bitnami/nginx --set replicaCount=2 | less   # render locally, no install

# Install / upgrade
helm install web bitnami/nginx -n web --create-namespace --set replicaCount=2
helm install web bitnami/nginx -f my-values.yaml --version 18.1.0
helm upgrade web bitnami/nginx -n web --set image.tag=1.27.1 --reuse-values
helm upgrade --install web bitnami/nginx -n web           # idempotent install-or-upgrade

# Inspect releases
helm list -A                        # all namespaces — the first command for "find the release"
helm list -A --pending              # releases stuck mid-operation
helm status web -n web
helm get values web -n web          # user-supplied values
helm get manifest web -n web        # what was actually applied
helm history web -n web

# Roll back / remove
helm rollback web 1 -n web
helm uninstall web -n web
Values precedence

Lowest to highest: chart's values.yaml → each -f file in order → each --set. On upgrade without --reuse-values, values you set last time are reset to chart defaults unless you pass them again.

2.5 Kustomize

Kustomize customizes plain YAML without templates. A base holds the common manifests; each overlay references the base and layers changes on top (namespace, name prefix, labels, image tags, patches). It's built into kubectl.

kustomize-example/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   └── service.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── replicas-patch.yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
- service.yaml
labels:
- pairs:
    app.kubernetes.io/name: web
  includeSelectors: true
---
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namespace: prod
namePrefix: prod-
images:
- name: myapp                  # matches the image name in the base
  newTag: v2.1.0
configMapGenerator:
- name: web-config
  literals:
  - LOG_LEVEL=warn             # generated name gets a content hash suffix
patches:
- path: replicas-patch.yaml
---
# overlays/prod/replicas-patch.yaml  (strategic merge patch)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 5
kubectl kustomize overlays/prod            # render to stdout — always check this first
kubectl apply -k overlays/prod             # build + apply
kubectl delete -k overlays/prod
Why the hash suffix? configMapGenerator names the ConfigMap e.g. web-config-7k2f9m and rewrites references to it. Changing the config changes the name, which changes the Pod template, which triggers a rollout — config changes roll out like code changes.
Key Takeaways — Chapter 2
  • Only template changes create a new ReplicaSet and a rollout
  • maxSurge / maxUnavailable bound a RollingUpdate; Recreate has downtime
  • rollout status / history / undo / pause / resume / restart
  • Blue-green = flip a Service selector; canary = shared label + replica ratio
  • HPA needs resource requests and metrics-server
  • helm list -A, get values, upgrade --install, rollback REV
  • Kustomize: base + overlays; render with kubectl kustomize, apply with -k
  • configMapGenerator hashes force rollouts on config change
Chapter 03

Application Observability & Maintenance

Exam weight · 15%

Kubernetes can only keep an application healthy if it can tell when it isn't. Probes give the kubelet that signal; logs, events and metrics give you the signal. This chapter covers both, then turns them into a repeatable debugging routine — the exam always has at least one "this Pod is broken, fix it" task — and finishes with API deprecations, the maintenance chore that breaks manifests across upgrades.

3.1 Probes

ProbeQuestion it answersOn failure
startupHas the app finished starting?Container restarted after failureThreshold × periodSeconds; liveness/readiness are paused until it succeeds
livenessIs the process stuck beyond recovery?Container is killed and restarted
readinessCan it serve traffic right now?Pod removed from Service endpoints (not restarted)
containers:
- name: api
  image: myapp:v1
  ports:
  - containerPort: 8080
  startupProbe:                 # slow starter: allow up to 30 x 5s = 150s
    httpGet:
      path: /healthz
      port: 8080
    failureThreshold: 30
    periodSeconds: 5
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    periodSeconds: 10
    failureThreshold: 3
  readinessProbe:
    httpGet:
      path: /ready
      port: 8080
    initialDelaySeconds: 5
    periodSeconds: 5
# The other mechanisms (any probe type can use any of them)
exec:
  command: ["cat", "/tmp/healthy"]      # exit code 0 = success

tcpSocket:
  port: 5432                            # TCP connect succeeds = success

grpc:
  port: 9090                            # standard gRPC health-checking protocol
FieldDefaultMeaning
initialDelaySeconds0Wait before the first probe
periodSeconds10How often to probe
timeoutSeconds1Probe call timeout
failureThreshold3Consecutive failures before acting
successThreshold1Consecutive successes to recover (must be 1 for liveness/startup)
Liveness probes cause outages: a liveness probe that checks a downstream dependency (the database) will restart every replica when the database blips — turning a partial outage into a total one. Liveness should check only "is this process wedged". Put dependency checks in readiness.

3.2 Logs, Events & Metrics

# Logs
kubectl logs web                          # single-container Pod
kubectl logs web -c sidecar               # pick a container
kubectl logs web --all-containers
kubectl logs web -f --tail=50             # follow, last 50 lines
kubectl logs web --since=10m --timestamps
kubectl logs web --previous               # the crashed instance — essential for CrashLoopBackOff
kubectl logs -l app=web --prefix          # every Pod matching a label
kubectl logs deploy/web                   # one Pod of the Deployment

# Events: the cluster's own log of what it tried and why it failed
kubectl get events --sort-by=.lastTimestamp
kubectl get events -n prod --field-selector type=Warning
kubectl get events --field-selector involvedObject.name=web
kubectl describe pod web                  # events are at the bottom

# Resource usage (requires metrics-server)

Exam pattern: "Write the name of the Pod using the most CPU in namespace X to /opt/answer.txt" → kubectl top pod -n X --sort-by=cpu --no-headers | head -1 | awk '{print $1}' > /opt/answer.txt. Then cat the file to check it.

Exit codes worth memorizing

0 — completed normally (in a Deployment that still restarts it!). 1 — generic app error. 126/127 — command not executable / not found (bad command). 137 = 128+9, SIGKILL — OOMKilled or failed liveness. 143 = 128+15, SIGTERM — normal graceful shutdown.

Fixing a running Pod: most Pod fields are immutable. kubectl edit pod saves your edits to /tmp/kubectl-edit-*.yaml when rejected; then kubectl replace --force -f /tmp/kubectl-edit-xxxx.yaml deletes and recreates it in one step.

Chapter 04

Application Environment, Configuration & Security

Exam weight · 25%

The heaviest domain on the exam. It's about everything around the container: extending the API with custom resources, who may do what (RBAC and ServiceAccounts), how much CPU and memory a workload may take, how configuration and secrets get in, and what the process is allowed to do once it's running.

4.1 CRDs & Operators

A CustomResourceDefinition teaches the API server a new kind. Once it exists you can kubectl get, apply and delete objects of that kind like any built-in. A CRD alone only stores data; an operator is a controller that watches those objects and reconciles the real world toward them (e.g. a PostgresCluster object becomes a StatefulSet, Services, backups…).

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.stable.example.com     # must be <plural>.<group>
spec:
  group: stable.example.com
  scope: Namespaced                    # or Cluster
  names:
    plural: backups
    singular: backup
    kind: Backup
    shortNames: ["bk"]
  versions:
  - name: v1
    served: true
    storage: true                      # exactly one version is the storage version
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              schedule:
                type: string
              retentionDays:
                type: integer
                minimum: 1
---
apiVersion: stable.example.com/v1
kind: Backup
metadata:
  name: nightly
spec:
  schedule: "0 2 * * *"
  retentionDays: 7
kubectl get crd
kubectl describe crd backups.stable.example.com
kubectl api-resources --api-group=stable.example.com
kubectl get backups            # or: kubectl get bk
kubectl explain backup.spec    # works because of the schema

4.2 Authentication & RBAC

Every request passes three gates: authentication (who are you — certificate, token, OIDC), authorization (may you do this — RBAC), and admission (is this object acceptable — §4.7). RBAC is additive: there are no deny rules, only permissions granted.

ObjectScopePurpose

ClusterRoleClusterSame, for cluster-scoped resources (nodes, PVs) or reusable across namespaces

apiVersion: rbac.authorization.k8s.io/v1
kind: Role

  name: pod-reader
  namespace: dev

- apiGroups: [""]                 # "" = core group (pods, services, configmaps...)

  resources: ["deployments"]
  verbs: ["get", "list", "update", "patch"]

Find the API group: kubectl api-resources prints each resource's group in the APIVERSION column — apps/v1 means group apps, v1 alone means the core group "".

4.3 ServiceAccounts

Users are humans (external to Kubernetes); ServiceAccounts are identities for workloads, living in a namespace. Every namespace has a default SA, and a Pod without serviceAccountName runs as it. The kubelet mounts a short-lived, auto-rotated token at /var/run/secrets/kubernetes.io/serviceaccount/token.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: ci-bot
  namespace: dev
automountServiceAccountToken: false     # opt out by default for this SA
---
apiVersion: v1
kind: Pod
metadata:
  name: deployer
  namespace: dev
spec:
  serviceAccountName: ci-bot
  automountServiceAccountToken: true    # Pod-level setting wins
  containers:
  - name: kubectl
    image: bitnami/kubectl:1.31
    command: ["sh", "-c", "kubectl get pods; sleep 3600"]
kubectl create serviceaccount ci-bot -n dev
kubectl set serviceaccount deployment/api ci-bot -n dev    # SA on an existing Deployment
kubectl create token ci-bot -n dev --duration=1h           # mint a token for testing

# From inside a Pod: call the API with the mounted token
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
curl -sk -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api/v1/namespaces/dev/pods
Pods can't switch SA in place: serviceAccountName on a running Pod is immutable. Set it on the Deployment (rolls new Pods), or recreate the Pod.

4.4 Requests, Limits & Quotas

Requests are what the scheduler reserves — a Pod lands only on a node with that much unreserved capacity. Limits are what the kernel enforces at runtime: exceeding the CPU limit means throttling, exceeding the memory limit means OOMKilled.

containers:
- name: api
  image: myapp:v1
  resources:
    requests:
      cpu: 250m          # 0.25 core; 1 = 1000m
      memory: 128Mi      # Mi/Gi are powers of 2; M/G powers of 10
    limits:
      cpu: 500m
      memory: 256Mi
kubectl set resources deployment/api -c api --requests=cpu=250m,memory=128Mi --limits=cpu=500m,memory=256Mi
kubectl run web --image=nginx --dry-run=client -o yaml   # then add resources by hand
QoS classConditionEviction order under pressure
GuaranteedEvery container has requests = limits for both CPU and memoryLast
BurstableAt least one request or limit set, not GuaranteedMiddle
BestEffortNo requests or limits at allFirst

LimitRange: per-container defaults and bounds

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: dev
spec:
  limits:
  - type: Container
    default:              # becomes limits if the container sets none
      cpu: 500m
      memory: 256Mi
    defaultRequest:       # becomes requests if the container sets none
      cpu: 100m
      memory: 64Mi
    max:
      cpu: "1"
      memory: 512Mi
    min:
      cpu: 50m

ResourceQuota: namespace-wide totals

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: dev
spec:
  hard:
    pods: "10"
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    configmaps: "20"
    persistentvolumeclaims: "5"
    count/deployments.apps: "5"
kubectl create quota team-quota -n dev --hard=pods=10,requests.cpu=2,requests.memory=2Gi,limits.cpu=4,limits.memory=4Gi
kubectl describe quota -n dev          # Used vs Hard
kubectl describe limitrange -n dev
Quota gotcha: once a quota covers requests.cpu or limits.memory, every new Pod in the namespace must specify them (or get them from a LimitRange), otherwise it's rejected: must specify limits.memory. For a Deployment, the error shows up in the ReplicaSet's events, not on the Deployment — kubectl describe rs.

kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 -d

kind: Pod

  name: configured

    - name: DB_PASSWORD               # single key from a Secret

          name: db-creds

    - name: POD_IP                    # Downward API
      valueFrom:

          fieldPath: status.podIP

    - configMapRef:
        name: env-cfg
    - secretRef:
        name: db-creds
      prefix: DB_

      readOnly: true
  volumes:

    configMap:
      name: nginx-conf
  - name: creds
    secret:
      secretName: db-creds
      defaultMode: 0400
      items:                          # mount only selected keys
      - key: password
        path: db-password
Env vars vs volumes on update

Environment variables are read once, at container start — editing the ConfigMap changes nothing until the Pod restarts (kubectl rollout restart). Volume-mounted ConfigMaps/Secrets are refreshed by the kubelet within about a minute — except when mounted with subPath, which never updates. Mark an object immutable: true to forbid edits and spare the API server the watches.

Secrets aren't secret by default: base64 is an encoding. Anyone who can get secrets in the namespace can read them. Protection comes from RBAC, encryption at rest, and keeping them out of git.

4.6 SecurityContext

A securityContext sets the Linux identity and privileges of the process. It exists at Pod level (applies to all containers) and container level (overrides the Pod level for that container). Some fields only exist at one level.

apiVersion: v1
kind: Pod
metadata:
  name: hardened
spec:
  securityContext:                    # Pod level
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000                     # volumes are group-owned by 2000
    runAsNonRoot: true                # refuse to start if the image would run as UID 0
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: myapp:v1
    securityContext:                  # container level (wins over Pod level)
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      privileged: false
      capabilities:
        drop: ["ALL"]
        add: ["NET_BIND_SERVICE"]      # bind ports below 1024 as non-root
    volumeMounts:
    - name: tmp
      mountPath: /tmp                 # writable scratch since root fs is read-only
  volumes:
  - name: tmp
    emptyDir: {}
FieldPodContainer
runAsUser / runAsGroup / runAsNonRoot / seccompProfile✓✓
fsGroup / supplementalGroups / sysctls✓—
capabilities / privileged / allowPrivilegeEscalation / readOnlyRootFilesystem—✓
# Verify
kubectl exec hardened -- id                       # uid=1000 gid=3000 groups=2000
kubectl exec hardened -- touch /test              # Read-only file system
kubectl exec hardened -- grep Cap /proc/1/status  # capability bitmasks

4.7 Admission & Pod Security

After authorization, admission controllers can mutate or reject an object before it's stored. Several you've already met are admission controllers: LimitRanger (injects defaults), ResourceQuota (rejects over-quota objects), ServiceAccount (injects the token). Clusters can add their own via validating/mutating webhooks (OPA Gatekeeper, Kyverno).

Pod Security Admission enforces the Pod Security Standards per namespace via labels:

LevelAllows
privilegedAnything
baselineBlocks known escalations: privileged, hostNetwork/hostPID, hostPath, added dangerous capabilities
restrictedBaseline + must run as non-root, drop ALL capabilities, no privilege escalation, seccomp RuntimeDefault
kubectl label namespace prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted
# Modes: enforce (reject), audit (log), warn (warning to the client)
Exam pattern: "A Deployment in namespace X has 0 Pods" → kubectl describe rs or kubectl get events -n X. The message (violates PodSecurity "restricted", exceeded quota) names exactly which field to add.

  • CRD = new kind in the API; operator = controller reconciling it
  • Role/RoleBinding are namespaced; a RoleBinding can grant a ClusterRole
  • Verify RBAC with auth can-i --as=system:serviceaccount:NS:NAME

Chapter 05

Services & Networking

Exam weight · 20%

The Kubernetes network model is flat: every Pod gets its own IP and can reach every other Pod without NAT. That's convenient but leaves two problems — Pod IPs change every time a Pod is replaced, and "everything can talk to everything" is a security liability. Services and DNS solve the first; NetworkPolicies solve the second; Ingress brings HTTP traffic in from outside.

5.1 Services

A Service is a stable virtual IP and DNS name in front of a set of Pods chosen by a label selector. The control plane keeps an EndpointSlice listing the IPs of matching, Ready Pods, and kube-proxy programs every node to load-balance the Service IP across them.

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP              # default
  selector:
    app: api                   # Pods with this label become endpoints
  ports:
  - name: http
    port: 80                   # the Service's port (what clients dial)
    targetPort: 8080           # the container's port (number or named port)
    protocol: TCP
TypeReachable fromNotes
ClusterIPInside the clusterDefault; virtual IP + DNS name
NodePortAny node's IP on a high port (30000–32767)Also gets a ClusterIP; set nodePort or let it be picked
LoadBalancerExternal cloud LBBuilds on NodePort; EXTERNAL-IP stays <pending> without a cloud controller
ExternalName—DNS CNAME to an external host; no proxying, no selector
Headless (clusterIP: None)Inside the clusterNo virtual IP; DNS returns Pod IPs directly — used by StatefulSets
# Generate Services imperatively
kubectl expose deployment api --port=80 --target-port=8080                    # ClusterIP
kubectl expose deployment api --port=80 --target-port=8080 --type=NodePort --name=api-np
kubectl create service nodeport api --tcp=80:8080 --node-port=30080 --dry-run=client -o yaml
kubectl run web --image=nginx --port=80 --expose                              # Pod + Service

kubectl get svc,endpoints api
kubectl get endpointslices -l kubernetes.io/service-name=api
expose vs create service: kubectl expose copies the selector from the target object's labels. kubectl create service generates selector app=<service-name>, which often won't match your Pods — check it before applying.

5.3 Ingress

An Ingress is a set of HTTP routing rules — host and path to Service — implemented by an Ingress controller (ingress-nginx, Traefik, HAProxy…). Without a controller, an Ingress object does nothing. ingressClassName selects which controller handles it.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /     # controller-specific
spec:
  ingressClassName: nginx
  tls:
  - hosts: ["shop.example.com"]
    secretName: shop-tls          # kubernetes.io/tls Secret
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix          # Prefix | Exact | ImplementationSpecific
        backend:
          service:
            name: api
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              name: http          # or by port name
  defaultBackend:                 # anything that matches no rule
    service:
      name: not-found
      port:
        number: 80
kubectl create ingress shop --class=nginx \
  --rule="shop.example.com/api*=api:80" \
  --rule="shop.example.com/*=frontend:80,tls=shop-tls"
# path ending in * => pathType Prefix; without * => Exact

kubectl get ingress
kubectl describe ingress shop      # backends + whether endpoints exist
curl -H "Host: shop.example.com" http://<node-ip>:<ingress-nodeport>/api
Prefix matching is by path element

pathType: Prefix with /api matches /api, /api/ and /api/v1 — but not /apiv2. When several paths match, the longest wins. Exact matches only the literal path.

Beyond Ingress: the Gateway API (Gateway, HTTPRoute) is Ingress's successor, with role separation and traffic splitting built in. Recognize it, but Ingress is what CKAD tasks usually ask for.

5.4 NetworkPolicies

By default all Pods accept traffic from anywhere. A NetworkPolicy selects Pods with podSelector; as soon as any policy selects a Pod for a direction (Ingress / Egress), that direction becomes deny-by-default for it, and only traffic matching some policy's rules is allowed. Policies are additive — allows from all policies are unioned. Enforcement requires a CNI that supports it (Calico, Cilium…).

# 1. Default deny all ingress and egress in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: prod
spec:
  podSelector: {}               # every Pod in the namespace
  policyTypes: ["Ingress", "Egress"]
---
# 2. API Pods accept traffic from frontend Pods (same ns) and from the monitoring ns, on 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-ingress
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: ["Ingress"]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: monitoring
    ports:
    - protocol: TCP
      port: 8080
---
# 3. API Pods may talk to the DB on 5432 and to DNS
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-egress
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: ["Egress"]
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: db
    ports:
    - port: 5432
  - ports:                      # no "to" = any destination, on these ports
    - port: 53
      protocol: UDP
    - port: 53
      protocol: TCP
The AND / OR trap. Inside one from list, separate items (each starting with -) are OR. Selectors in the same item are AND. One dash changes the meaning completely: 
# OR: any Pod labelled role=client in THIS namespace, OR any Pod in namespace team-a
- from:
  - podSelector:
      matchLabels: { role: client }
  - namespaceSelector:
      matchLabels: { kubernetes.io/metadata.name: team-a }

# AND: only Pods labelled role=client that live in namespace team-a
- from:
  - podSelector:
      matchLabels: { role: client }
    namespaceSelector:
      matchLabels: { kubernetes.io/metadata.name: team-a }
Don't forget DNS: after a default-deny egress, nothing resolves names, so even allowed connections "time out". Always add the port 53 UDP+TCP egress rule. And remember the namespace label kubernetes.io/metadata.name is set automatically on every namespace. 
# Test from a Pod that carries (or doesn't carry) the allowed label
kubectl run t --rm -it --image=busybox:1.36 --restart=Never -l app=frontend -n prod -- wget -qO- -T 2 http://api:8080
kubectl run t --rm -it --image=busybox:1.36 --restart=Never -n prod -- wget -qO- -T 2 http://api:8080   # should time out
kubectl describe networkpolicy api-ingress -n prod

5.5 Troubleshooting Connectivity

"The Service doesn't work" almost always comes down to one of five things. Check them in order:

  1. Endpoints empty? kubectl get endpoints api. Empty means the selector matches no Ready Pods — compare kubectl get svc api -o yaml's selector with kubectl get pods --show-labels, and check readiness.
  2. Wrong targetPort? Endpoints exist but connections are refused: targetPort must be the port the container actually listens on (kubectl exec pod -- netstat -tlnp or check the image docs).
  3. Wrong namespace / name? Short name only works in the same namespace — use svc.namespace.
  4. NetworkPolicy? kubectl get netpol -A; connections hang (timeout) rather than being refused.
  5. Ingress? kubectl describe ingress — wrong service name/port, missing ingressClassName, or the host header doesn't match.
# One-liner sanity check from inside the cluster
kubectl run t --rm -it --image=busybox:1.36 --restart=Never -- sh -c \
  'nslookup api.prod && wget -qO- -T 2 http://api.prod:80 && echo OK'

# Bypass the Service: hit a Pod IP directly
kubectl get pod -l app=api -o wide
kubectl run t --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- -T 2 http://10.244.1.7:8080
Key Takeaways — Chapter 5
  • Service = stable IP + DNS over Ready Pods matching a selector
  • port is what clients dial; targetPort is what the container listens on
  • kubectl expose copies selectors; create service guesses app=NAME
  • svc, svc.ns, svc.ns.svc.cluster.local; headless gives per-Pod DNS
  • Ingress needs a controller and ingressClassName; Prefix matches by path element
  • Any policy selecting a Pod makes that direction deny-by-default
  • Separate list items = OR; selectors in one item = AND
  • Empty endpoints → labels/readiness; refused → targetPort; timeout → NetworkPolicy

Most people who fail the CKAD know enough Kubernetes. They run out of time. The exam rewards speed with kubectl as much as knowledge: generating YAML instead of typing it, finding a field name in ten seconds instead of two minutes, and never losing points to the wrong namespace or context.

6.5 Time Management & Verification

The per-task routine

1. Switch context — copy the kubectl config use-context … line from the task, every time. 2. Note the namespace — add -n or set it with kn. 3. Generate, edit, apply. 4. Verify — get/describe the object, check the Pod is Running and Ready, curl it, cat any output file. 5. Move on.

  • Triage first. Weights differ. A 2% task that's eating ten minutes isn't worth it — flag it and come back.
  • Partial credit exists. Tasks are scored on several checks; getting the Deployment right with a wrong label still earns something.
  • Don't wait. Pulling images or waiting for a rollout? Start reading the next task.
  • Use exact names. Resource names, container names, file paths, label keys — copy them from the task text; a typo fails the check.
  • Save files where asked. If the task says "save the manifest to /opt/ckad/pod.yaml", the checker looks there.
  • Leave things running. Don't delete objects the task created unless told to.
# Fast verification snippets
k get pod web -o wide && k describe pod web | tail -20
k get deploy,rs,pods -l app=api
k rollout status deploy/api --timeout=60s
k auth can-i list secrets --as=system:serviceaccount:dev:bot -n dev
k run t --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- -T 2 http://svc.ns
cat /opt/answer.txt
Practice loop: do each domain's tasks on a local cluster (kind, minikube, k3d) until the imperative commands are muscle memory, then run full timed mock exams (killer.sh, or a local simulator such as CK-X). Aim to finish a mock with 20+ minutes to spare before booking the real one.

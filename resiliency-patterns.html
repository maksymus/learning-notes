Chapter 01

Failure & the Principles of Fault Tolerance

A single process running on one machine has a simple failure model: it is either up or down. The moment you split that process into services talking over a network, you inherit a far richer — and far nastier — set of failure modes. This chapter builds the mental model the rest of the course rests on: what partial failure means, what the CAP theorem actually constrains, how to put a number on reliability, and how failures threaten not just availability but the correctness of your data.

1.1 Distributed Systems & Partial Failure

Leslie Lamport's definition still lands: "A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable." The defining property is partial failure — some components are working while others are not, and crucially you cannot reliably tell which.

When you call a remote service and the call times out, you genuinely do not know whether:

  • The request never arrived (network dropped it on the way out).
  • The request arrived, was processed, and the response was lost on the way back.
  • The peer is alive but slow, and the work is still running.
  • The peer crashed mid-operation, leaving partial state behind.

This ambiguity is the root of most resiliency complexity. A retry is safe in case (1) and dangerous in case (2). The two generals problem proves that no protocol over an unreliable channel can guarantee both sides agree to act — which is why we reach for idempotency and timeouts rather than perfect coordination.

Reliability vs Availability vs Fault Tolerance

Reliability is the probability the system performs correctly over a time interval (MTBF — mean time between failures). Availability is the fraction of time it is usable (a function of MTBF and MTTR — mean time to recovery). Fault tolerance is the system's ability to keep operating correctly despite faults. A system can be highly available but unreliable (up, but returning wrong answers), so the three are not interchangeable.

The fallacies of distributed computing

Peter Deutsch's eight fallacies are assumptions engineers keep making and keep regretting:

  1. The network is reliable.
  2. Latency is zero.
  3. Bandwidth is infinite.
  4. The network is secure.
  5. Topology doesn't change.
  6. There is one administrator.
  7. Transport cost is zero.
  8. The network is homogeneous.

Cascading failures

A cascading failure is when the failure of one component overloads the others until the whole system collapses. The classic shape: service B slows down → service A's threads block waiting on B → A's connection pool exhausts → A starts failing requests it could otherwise serve → A's callers retry → the retry storm hits B even harder. The system has crossed from a localized problem into a metastable failure that persists even after the original trigger is gone.

// Anatomy of a cascade: an unbounded worker that amplifies a downstream stall.
// Each slow call to `payments` holds a goroutine AND a DB connection.
func handleCheckout(w http.ResponseWriter, r *http.Request) {
    conn := dbPool.Get()          // limited resource (say 100 connections)
    defer conn.Close()

    // If payments is slow, this blocks for the full client timeout.
    // 1000 concurrent checkouts -> pool exhausted -> EVERY endpoint fails,
    // not just checkout. The blast radius is the whole service.
    resp, err := paymentsClient.Charge(r.Context(), order)
    if err != nil {
        http.Error(w, "payment failed", 502)
        return
    }
    _ = conn.Save(resp)
}

The defenses against cascades — timeouts, bulkheads, circuit breakers, load shedding — are exactly the patterns of Chapters 2 and 3. Keep this picture in mind: almost every pattern in this course exists to contain blast radius.

1.2 The CAP Theorem & PACELC

Eric Brewer's CAP theorem states that a distributed data store can provide at most two of the following three guarantees simultaneously:

PropertyMeaning
ConsistencyEvery read sees the most recent write (linearizability) — all nodes agree.
AvailabilityEvery request to a non-failing node gets a non-error response.
Partition toleranceThe system keeps working despite messages being lost between nodes.

The common phrasing "pick two" is misleading. In any real network, partitions happen — cables get cut, switches reboot, GC pauses make a node unreachable. So P is not optional. The real choice CAP forces is: when a partition occurs, do you sacrifice C or A?

  • CP system — refuse writes on the minority side to keep data consistent. Example: a quorum store like etcd/ZooKeeper, or Postgres with synchronous replication. You lose availability for the partitioned clients.
  • AP system — accept writes on both sides and reconcile later. Example: Cassandra, DynamoDB in eventually-consistent mode. You stay up but readers may see stale or conflicting data.
Common misconception: CAP's "consistency" is linearizability, a much stronger guarantee than the "C" in ACID. A system can be CAP-inconsistent yet still enforce ACID transactions locally. Don't conflate the two C's.

PACELC — the part CAP forgets

CAP only describes behaviour during a partition. Daniel Abadi's PACELC extends it: if there is a Partition, choose A or C; Else (normal operation) choose Latency or Consistency. This captures the everyday trade-off: even with no partition, synchronous replication for strong consistency costs you latency. DynamoDB is PA/EL (favours availability and latency); a strongly-consistent store like Spanner is PC/EC.

1.3 SLA, SLO, SLI & the Nines

These three acronyms are constantly confused. The relationship is a hierarchy:

TermWhat it isAudience
SLI — IndicatorA measured number: e.g. "ratio of requests served in <200 ms" or "successful requests / total".Engineers (the raw signal)
SLO — ObjectiveA target for an SLI: "99.9% of requests succeed over 30 days". Internal goal.The team
SLA — AgreementA contract with consequences (refunds, credits) if the SLO is missed.Customers / legal

Set your SLO stricter than your SLA, so you have a buffer to react before you owe anyone money. The gap between 100% and your SLO is your error budget — the amount of unreliability you are allowed to spend on releases, experiments, and risk. If you have budget left, ship faster; if you've burned it, freeze and stabilize.

Composition kills nines. If a request depends on 5 services that are each 99.9% available, and the failures are independent, the end-to-end availability is 0.999⁵ ≈ 99.5% — worse than any single component. This is why fan-out architectures need redundancy and fallbacks, not just individually reliable services. 
// Computing an availability SLI from request counts (a "request-based" SLO).
type Window struct {
    Total int64
    Good  int64 // requests that met the latency+success bar
}

func (w Window) SLI() float64 {
    if w.Total == 0 {
        return 1.0
    }
    return float64(w.Good) / float64(w.Total)
}

// Error budget remaining, given a 30-day 99.9% objective.
func errorBudgetRemaining(w Window, objective float64) float64 {
    allowedBad := float64(w.Total) * (1 - objective) // budget of failures
    actualBad := float64(w.Total - w.Good)
    return (allowedBad - actualBad) / allowedBad // 1.0 = full, <0 = blown
}

1.4 Failures & Data Integrity

Downtime is recoverable — you restart and serve again. Corrupted or lost data is often not. The most dangerous failures are the ones that violate integrity: an invariant of your data that must always hold (an account balance never goes negative; an order is never charged twice; a message is never processed out of order in a way that breaks state).

Idempotency

An operation is idempotent if applying it multiple times has the same effect as applying it once. Idempotency is the single most important tool for surviving the "did my request actually happen?" ambiguity from §1.1 — if retries are safe, the ambiguity stops mattering.

  • GET, PUT, DELETE are idempotent by HTTP semantics; POST is not.
  • SET balance = 100 is idempotent; balance = balance + 100 is not.
  • The usual fix for non-idempotent operations: an idempotency key supplied by the client, stored server-side, so a replay returns the original result instead of repeating the effect.
// Idempotent "charge once" keyed by a client-supplied token.
func (s *Server) Charge(ctx context.Context, key string, amount int64) (Receipt, error) {
    // First, atomically claim the key. If it already exists, return the
    // stored receipt instead of charging again.
    if r, ok, err := s.store.Get(ctx, key); err != nil {
        return Receipt{}, err
    } else if ok {
        return r, nil // replay -> same result, no double charge
    }

    receipt, err := s.gateway.Capture(ctx, amount)
    if err != nil {
        return Receipt{}, err
    }
    // Store under the key. Use INSERT ... ON CONFLICT DO NOTHING to win the race
    // if two retries arrive concurrently.
    if err := s.store.PutIfAbsent(ctx, key, receipt); err != nil {
        return Receipt{}, err
    }
    return receipt, nil
}

Split-brain & failover

Failover is promoting a standby to primary when the primary appears dead. Split-brain is the catastrophe that happens when the old primary wasn't actually dead (just partitioned or paused) and you now have two primaries accepting writes. Both diverge, and reconciling them later can mean silently dropping someone's data. Defenses:

  • Fencing tokens — a monotonically increasing number issued on each leadership change; storage rejects writes carrying a stale token.
  • Quorum / majority — a node may only act as leader if it can reach a majority, so two leaders are impossible.
  • STONITH ("shoot the other node in the head") — forcibly power-off the suspected-dead node before promoting.

Quorum reads and writes

In a replicated store with N replicas, require W acknowledgements to commit a write and R replicas to serve a read. If W + R > N, every read set overlaps every write set by at least one replica, so a read is guaranteed to see the latest committed write — strong consistency from quorum overlap. Common choice for N=3: W=2, R=2.

Tuning W and R

W=N, R=1 makes reads fast but writes fragile (any replica down blocks writes). W=1, R=N is the mirror. W=R=⌈(N+1)/2⌉ (majority quorum) balances both and tolerates ⌊N/2⌋ failures. Lowering W+R below N+1 gives you an AP system (eventual consistency) — faster, but reads can be stale.

1.5 Durability: WAL, Replication & Idempotency in Practice

Why Postgres needs a WAL

A Write-Ahead Log is the cornerstone of crash-safe durability. The rule is simple and absolute: before any change is applied to the data files, a record describing that change is flushed to the log (and fsync'd to disk). If the database crashes mid-transaction, on restart it replays the WAL to redo committed changes and discards uncommitted ones, restoring a consistent state.

The WAL is also what makes Postgres replication and point-in-time recovery possible: a replica simply streams and replays the primary's WAL. The trade-off you control is synchronous_commit — whether a COMMIT waits for the WAL to be durably on disk (and on replicas) before returning. Turning it off is faster but means a crash can lose recently "committed" transactions.

WAL is durability, not isolation. The WAL guarantees a committed transaction survives a crash; it says nothing about concurrent transactions seeing consistent snapshots — that's MVCC's job. Resilient systems need both.

Why Kafka needs replication factor > 1

A Kafka topic is split into partitions; each partition has one leader and zero or more follower replicas. The replication factor is how many copies exist. With RF=1, the loss of a single broker means permanent data loss for every partition it led. With RF=3 and min.insync.replicas=2, a producer using acks=all only gets an acknowledgement once the data is on at least two replicas — so a single broker failure loses nothing.

SettingEffect
acks=0Fire and forget. Fastest, zero durability.
acks=1Leader has it. Lost if leader dies before replication.
acks=all + min.insync.replicas=2At least 2 replicas have it before ack. Survives 1 broker loss. The durable default.

How a payment provider handles duplicate payments

Payment systems like YooKassa, Stripe, or PayPal live or die by idempotency. The flow that prevents a customer being charged twice when the network hiccups:

  1. Client generates an idempotency key (a UUID) for the payment before sending.
  2. The first request creates the payment and stores it under the key.
  3. Any retry with the same key returns the same payment object — the gateway never captures twice.
  4. The provider notifies the merchant via an idempotent webhook; the merchant deduplicates on payment ID, because webhooks are delivered at least once and can arrive twice.

This is the same idempotency-key pattern from §1.4, applied end to end across an untrusted network — the canonical real-world example of designing for "I don't know if my request went through."

1.6 BigTech Incidents & Lessons

Every pattern in this course was paid for in a real outage. Five worth knowing:

GitHub — 24h of degraded service (Oct 2018)

A 43-second network partition between the US East Coast and West Coast data centers triggered an automatic failover of the MySQL cluster. When connectivity returned, the two sides had divergent writes — a textbook split-brain. GitHub chose consistency over availability: rather than risk corrupting data by auto-merging, engineers spent ~24 hours manually reconciling. Lesson: automated failover without robust fencing and quorum can be worse than the failure it's trying to fix.

AWS us-east-1 — the region that takes the internet down

Multiple times (2017 S3, 2020 Kinesis, 2021 networking), failures in AWS's oldest and busiest region have cascaded across hundreds of dependent services worldwide — because so much of the internet, and AWS's own control plane, has hidden dependencies on us-east-1. Lesson: a shared dependency is a shared point of failure; "multi-AZ" is not "multi-region," and control planes need to be as redundant as data planes.

Facebook / Instagram / WhatsApp — the 6-hour BGP outage (Oct 2021)

A faulty configuration change withdrew Facebook's BGP routes, making their DNS servers unreachable, which made everything unreachable — including the internal tools and badge systems engineers needed to fix it. The outage wiped roughly $6 billion off the company's market value in hours. Lesson: beware circular dependencies in your recovery path — your tooling must not depend on the system it's meant to repair.

GitLab — the database deletion (Jan 2017)

An engineer fighting a replication issue ran rm -rf on what they believed was a stale directory — it was the primary database's data directory. They then discovered that five separate backup mechanisms had all silently failed: the recovery ultimately relied on a six-hour-old staging snapshot one engineer happened to have. Lesson: an untested backup is not a backup. Restores must be rehearsed, not assumed.

The common thread

None of these were caused by exotic bugs. They were caused by automation behaving correctly but unwisely (GitHub), hidden shared dependencies (AWS, Facebook), and unverified safety nets (GitLab). Resilience is less about preventing faults — faults are inevitable — and more about limiting their blast radius and guaranteeing a recovery path.

Key Takeaways — Chapter 1
  • Partial failure means you often can't tell whether a request succeeded — design for that ambiguity
  • Partitions are inevitable, so CAP really asks: during a partition, sacrifice C or A?
  • PACELC adds the everyday trade-off: even without partitions, you trade latency for consistency
  • SLI is measured, SLO is your target, SLA is the contract; the gap to 100% is your error budget
  • Composing N services multiplies their failure probabilities — fan-out erodes the nines
  • Idempotency keys, quorums (W+R>N), fencing tokens, WAL, and RF>1 are the durability primitives
Chapter 02

Handling Errors & Transient Failures

The database blips for a second. A third-party API answers in 30 seconds instead of 30 milliseconds. The link between two services drops three packets and recovers. In a distributed system these events are not exceptions — they are the weather. Reacting to them correctly is, as the course material puts it, the barrier between a mid-level and a senior engineer. This chapter covers the full toolbox: retries, backoff, timeouts, cancellation, circuit breakers, and graceful degradation.

2.1 Retries Done Right

A retry is the simplest resiliency pattern and the easiest to get catastrophically wrong. Two questions govern every retry decision:

  1. Is this error transient? Retry a connection reset, a 503, a timeout. Never retry a 400, a 404, or a validation error — the result will be identical and you're just wasting capacity.
  2. Is the operation safe to repeat? Only retry if it's idempotent (§1.4) or guarded by an idempotency key. Retrying a non-idempotent "create order" can create two orders.
RetryDo NOT retry
Connection refused / reset400 Bad Request
Timeout (deadline exceeded)401 / 403 (auth)
503 Service Unavailable404 Not Found
429 Too Many Requests (with backoff)422 Unprocessable Entity
Leader election in progressAny business-logic rejection
Retry storms. Naïve retries amplify load exactly when a service is already struggling. If every client retries 3× during a brownout, you've tripled the traffic to a service that's failing because it's overloaded. Always combine retries with backoff (§2.2), a retry budget, and a circuit breaker (§2.5).

Retry budgets

Cap retries as a fraction of total traffic, not per-request. A retry budget of 10% means "across all requests, retries may add at most 10% extra load." When the budget is exhausted, stop retrying even if individual calls fail. This converts an exponential retry storm into a bounded, survivable overhead.

2.2 Backoff & Jitter

If you must retry, do not retry immediately, and do not retry on a fixed schedule. Exponential backoff increases the wait after each attempt (base, 2×base, 4×base…), giving the struggling dependency room to recover. But pure exponential backoff has a hidden flaw: if 1000 clients all failed at the same instant, they all back off by the same amount and retry in synchronized waves — re-creating the thundering herd.

The fix is jitter: randomize the delay so retries spread out over time. AWS's well-known analysis compares four strategies:

StrategyFormula (attempt n)Verdict
No jitterbase · 2ⁿSynchronized retry waves. Avoid.
Full jitterrand(0, base · 2ⁿ)Best spread; recommended default.
Equal jitterhalf + rand(0, half)Guarantees a minimum wait; slightly less spread.
Decorrelatedmin(cap, rand(base, prev·3))Great for long retry chains.
// Exponential backoff with full jitter and a deadline.
func retryWithBackoff(ctx context.Context, op func() error) error {
    const (
        base   = 100 * time.Millisecond
        cap    = 10 * time.Second
        maxTry = 6
    )
    var err error
    for attempt := 0; attempt < maxTry; attempt++ {
        if err = op(); err == nil {
            return nil
        }
        if !isRetryable(err) {
            return err // fail fast on permanent errors
        }
        // Full jitter: random point in [0, backoff].
        backoff := time.Duration(math.Min(float64(cap),
            float64(base)*math.Pow(2, float64(attempt))))
        sleep := time.Duration(rand.Int63n(int64(backoff)))

        select {
        case <-time.After(sleep):
        case <-ctx.Done(): // respect the caller's deadline
            return ctx.Err()
        }
    }
    return fmt.Errorf("exhausted retries: %w", err)
}
Honour Retry-After. When a server returns 429 or 503 with a Retry-After header, it is telling you exactly how long to wait. Use it instead of your computed backoff — the server knows its own recovery timeline better than you do.

2.3 Idempotency & Hedging

Retries and idempotency are inseparable. §1.4 covered idempotency keys; here's the operational rule: any code path that can be retried must be idempotent, or the retry must be suppressed. Make this explicit in your client — a request should carry a flag or key that says "this is safe to replay."

Hedging

Hedged requests attack tail latency rather than failure. The idea: if a request hasn't responded within, say, the 95th-percentile latency, send a second identical request to another replica and take whichever responds first, cancelling the loser. A small fraction of duplicated work buys a dramatic reduction in p99/p99.9 latency, because you route around a single slow node.

// Hedged request: fire a backup after a delay, return the first success.
func hedge(ctx context.Context, delay time.Duration,
    call func(context.Context) (Result, error)) (Result, error) {

    ctx, cancel := context.WithCancel(ctx)
    defer cancel() // cancels the loser as soon as we return

    type out struct {
        r   Result
        err error
    }
    results := make(chan out, 2)
    launch := func() { r, err := call(ctx); results <- out{r, err} }

    go launch()                       // primary
    timer := time.NewTimer(delay)
    defer timer.Stop()

    for received := 0; received < 2; {
        select {
        case <-timer.C:
            go launch()               // backup after `delay`
        case o := <-results:
            received++
            if o.err == nil {
                return o.r, nil       // first success wins
            }
        case <-ctx.Done():
            return Result{}, ctx.Err()
        }
    }
    return Result{}, errors.New("all hedged attempts failed")
}
Hedging requires idempotency and a cap on duplication (e.g. hedge at most 1–5% of requests). Hedging non-idempotent writes doubles your side effects. Hedging everything doubles your load.

2.4 Timeouts, Deadlines & Cancellation

A request without a timeout is a resource leak waiting to happen. If you never give up, a single stalled dependency will accumulate blocked goroutines, threads, and connections until you hit the cascade of §1.1. Every network call must have a bound.

Timeout vs deadline

A timeout is a duration ("give up after 2s"). A deadline is an absolute point in time ("give up at 12:00:03.0"). Deadlines compose correctly across a call chain: if the user's request has a 3-second deadline and you've already spent 2.5s, the downstream call inherits only the remaining 0.5s. Propagating a deadline rather than re-setting a fresh timeout at each hop is what prevents the total latency budget from being silently multiplied.

// In Go, context.Context carries the deadline and threads cancellation
// through the entire call tree.
func (h *Handler) Get(w http.ResponseWriter, r *http.Request) {
    // The incoming request may already carry a deadline; we tighten it.
    ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
    defer cancel() // ALWAYS cancel to release the timer + signal children

    // Each downstream call sees the SAME shrinking deadline. If the user's
    // budget is gone, the DB call fails fast instead of doing doomed work.
    user, err := h.users.Load(ctx, id)
    if errors.Is(err, context.DeadlineExceeded) {
        http.Error(w, "upstream timeout", http.StatusGatewayTimeout)
        return
    }
    ...
}

Cancellation propagation

When a client hangs up, or an upstream deadline fires, that cancellation should flow downstream so every service stops working on a result nobody will read. This is cancel propagation: a cancelled context aborts the DB query, closes the outbound HTTP call, and frees the connection — turning wasted work into reclaimed capacity. Without it, a user who refreshes an impatient page leaves a trail of zombie work amplifying load on an already-slow system.

Choosing timeout values

Set timeouts from your latency distribution, not gut feel. A good starting point is slightly above p99 of healthy latency — high enough that normal slow requests succeed, low enough that a truly stuck call is cut quickly. The total client deadline should be less than the sum of all downstream timeouts, so the client gives up before doing pointless retries against an already-doomed request.

2.5 The Circuit Breaker

Retries and timeouts handle individual failures. A circuit breaker handles a dependency that is persistently failing — it stops you from hammering a service that's already down, giving it room to recover and failing your own requests fast instead of slow. The name comes from electrical breakers: when current is dangerous, trip the circuit.

A breaker is a state machine with three states:

StateBehaviourTransition
ClosedRequests flow through; failures are counted.Failure rate exceeds threshold → Open
OpenRequests fail immediately (no call made). Fast failure protects the dependency and the caller.After a cool-down timeout → Half-Open
Half-OpenA limited number of trial requests are allowed through to probe recovery.Trials succeed → Closed; any fails → Open
// A minimal circuit breaker. Production options: sony/gobreaker, resilience4j.
type Breaker struct {
    mu          sync.Mutex
    state       State // Closed, Open, HalfOpen
    failures    int
    threshold   int
    openUntil   time.Time
    cooldown    time.Duration
}

var ErrOpen = errors.New("circuit breaker is open")

func (b *Breaker) Do(op func() error) error {
    b.mu.Lock()
    switch b.state {
    case Open:
        if time.Now().Before(b.openUntil) {
            b.mu.Unlock()
            return ErrOpen           // fail fast, no downstream call
        }
        b.state = HalfOpen           // cool-down elapsed: probe
    }
    b.mu.Unlock()

    err := op()

    b.mu.Lock()
    defer b.mu.Unlock()
    if err != nil {
        b.failures++
        if b.state == HalfOpen || b.failures >= b.threshold {
            b.state = Open           // trip (or re-trip)
            b.openUntil = time.Now().Add(b.cooldown)
        }
        return err
    }
    b.failures = 0                   // success: reset
    b.state = Closed
    return nil
}
Breaker vs retry — they cooperate. Retries handle a single blip; the breaker handles a sustained outage by stopping the retries once it's clear the dependency is down. Put the breaker outside the retry loop: trip on the aggregate, retry within a closed circuit.

2.6 Graceful Degradation & Fallback

When a dependency is down and the breaker is open, you have a choice: return an error, or degrade gracefully — serve a reduced-but-useful response. Good degradation is invisible or nearly so to the user.

  • Fallback to cache — recommendations service down? Serve last-known-good or a generic popular list from cache.
  • Fallback to a default — pricing/personalization service down? Show the standard price, not an error page.
  • Feature toggle / shedding — under load, disable the expensive "people also bought" widget but keep checkout working.
  • Stale-while-revalidate — serve slightly stale data and refresh in the background (Chapter 5).
// Fallback chain: breaker-protected primary, then cache, then a safe default.
func (s *Catalog) Recommendations(ctx context.Context, user string) []Item {
    var items []Item
    err := s.breaker.Do(func() error {
        var e error
        items, e = s.recoService.Get(ctx, user) // primary path
        return e
    })
    if err == nil {
        s.cache.Set(user, items) // refresh good data for future fallbacks
        return items
    }

    if cached, ok := s.cache.Get(user); ok {
        return cached            // degraded: last-known-good
    }
    return s.popularToday        // degraded: generic, but never an error page
}
Degradation must be a deliberate product decision. "Show stale prices" might be fine for a catalog and disastrous for a trading platform. Decide per feature whether stale/partial/empty is acceptable, and make the degraded state observable so it doesn't hide a real outage.
The layered defense

These patterns compose into a stack. From the inside out: timeout bounds each call → retry + backoff + jitter handles blips → circuit breaker handles sustained outages → fallback / graceful degradation keeps the user experience alive → bulkhead (Chapter 3) contains the blast radius. No single pattern is sufficient; resilience is the stack.

  • Exponential backoff with full jitter prevents synchronized retry storms
  • Retry budgets bound the amplification; honour Retry-After when given

  • Propagate deadlines (not fresh timeouts) and cancellation through the whole call tree

Chapter 03

Load Control & Balancing

A sudden traffic spike, one slow database query, or a struggling neighbour service can take down a healthy process if it has no defenses. Chapter 2 was about reacting to failures; this chapter is about staying stable under load — isolating resources so one failure can't sink the ship, limiting how much work you accept, collapsing duplicate work, and spreading traffic intelligently.

3.1 Resource Isolation & the Bulkhead

The bulkhead pattern is named after the watertight compartments in a ship's hull: if one floods, the others keep the ship afloat. In software, you partition resources so that the exhaustion of one pool cannot starve unrelated work.

The canonical failure it prevents: a single shared thread/connection pool. If endpoint A calls a slow dependency and A's traffic consumes all the shared connections, endpoints B and C fail too — even though their dependencies are perfectly healthy. Give each dependency (or each tenant, or each priority class) its own bounded pool, and A's problem stays A's problem.

// Bulkhead via a bounded semaphore per dependency. When a pool is exhausted,
// callers fail fast instead of piling up and starving other dependencies.
type Bulkhead struct{ sem chan struct{} }

func NewBulkhead(maxConcurrent int) *Bulkhead {
    return &Bulkhead{sem: make(chan struct{}, maxConcurrent)}
}

func (b *Bulkhead) Do(ctx context.Context, op func() error) error {
    select {
    case b.sem <- struct{}{}: // acquire a slot
        defer func() { <-b.sem }()
        return op()
    case <-ctx.Done():
        return ctx.Err()
    default:
        return errors.New("bulkhead full: shedding to protect other work")
    }
}

// payments and search get independent pools — a payments stall can't
// consume the slots that search needs.
var paymentsBulkhead = NewBulkhead(20)
var searchBulkhead   = NewBulkhead(50)

A related idea is the shuffle-sharding used by AWS: assign each customer a small random subset of nodes, so a single bad customer (or poisoned request) degrades only the few customers who happen to share its shard, not everyone.

3.2 Rate Limiting In Depth

A rate limiter caps how much work a client (or the whole system) may do per unit time. It protects you from spikes, abusive clients, and runaway retries. There are several algorithms with meaningfully different behaviour:

Token bucket

A bucket holds up to B tokens and refills at R tokens/second. Each request consumes a token; if the bucket is empty, the request is rejected (or waits). This is the most popular choice because it permits bursts up to the bucket size while enforcing an average rate R — matching how real traffic actually arrives.

// Token bucket. The stdlib golang.org/x/time/rate is a production-grade version.
type TokenBucket struct {
    mu       sync.Mutex
    tokens   float64
    capacity float64
    rate     float64 // tokens per second
    last     time.Time
}

func (tb *TokenBucket) Allow() bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()

    now := time.Now()
    // Refill based on elapsed time, capped at capacity.
    elapsed := now.Sub(tb.last).Seconds()
    tb.tokens = math.Min(tb.capacity, tb.tokens+elapsed*tb.rate)
    tb.last = now

    if tb.tokens >= 1 {
        tb.tokens--
        return true
    }
    return false // throttled -> return 429 with a Retry-After
}

3.3 Single Flight

Single flight (a.k.a. request collapsing / coalescing) ensures that when many identical requests arrive concurrently, only one actually executes and the rest share its result. It's a precise tool against duplicated expensive work — the same idea that defeats the cache "thundering herd" in Chapter 5.

// Go's golang.org/x/sync/singleflight collapses concurrent identical calls.
var group singleflight.Group

func (s *Service) GetUser(ctx context.Context, id string) (*User, error) {
    // If 1000 goroutines call GetUser("42") at once, the loader runs ONCE.
    // The other 999 block and receive the same (*User, error).
    v, err, shared := group.Do(id, func() (interface{}, error) {
        return s.loadFromDB(ctx, id) // the single expensive load
    })
    if err != nil {
        return nil, err
    }
    _ = shared // true if the result was shared with other callers
    return v.(*User), nil
}
Single flight couples callers. Because they share one execution, they share its failure and its context/deadline. One slow caller's cancellation can affect the shared call. Use DoChan with per-caller selects, or scope keys carefully, when callers have different deadlines.

3.4 Backpressure & Load Shedding

When demand exceeds capacity, you have exactly two honest options: slow the producers down (backpressure) or drop work (load shedding). The dishonest option — accept everything and queue it unboundedly — leads to memory exhaustion, ballooning latency, and eventual collapse. An unbounded queue is a latency bomb.

Backpressure

Backpressure is flow control: the consumer signals the producer to slow down. TCP does it with its receive window; gRPC and HTTP/2 do it with stream-level flow control; a bounded channel does it by blocking the sender. The key is that the signal propagates upstream so the pressure is felt at the source rather than absorbed silently.

Load shedding

When you can't slow producers (e.g. public internet traffic), shed load: reject excess requests quickly and cheaply before they consume real resources. The goal is to keep serving the requests you accept at full quality rather than serving everyone slowly. Crucially, shed by priority — drop the health-check-retry and the speculative prefetch before you drop the paying customer's checkout.

// Adaptive load shedding based on a queue-depth / latency signal.
func (s *Server) admit(req Request) bool {
    inflight := s.inflight.Load()
    if inflight < s.softLimit {
        return true // healthy: admit everything
    }
    if inflight >= s.hardLimit {
        // Overloaded: shed by priority, cheapest rejection possible.
        return req.Priority == Critical
    }
    // Degraded zone: probabilistically shed low-priority work.
    return req.Priority >= High || rand.Float64() > s.shedProbability()
}
Little's Law — why queues betray you

Little's Law says L = λ·W: the average number of in-flight requests (L) equals arrival rate (λ) times average latency (W). When a dependency slows (W rises) at constant arrival rate, in-flight count rises proportionally — exhausting threads, memory, and connections. This is the math behind cascading failure, and why bounding the queue (shedding) is not optional under overload.

3.5 Load Balancing & Health Checks

A load balancer spreads requests across a pool of upstream servers. Balancing can live on the client (the caller picks an instance, as in gRPC client-side LB or a service mesh) or on the server side (a dedicated LB like nginx, HAProxy, or an L4/L7 cloud balancer). Client-side avoids an extra hop and single choke point; server-side is simpler and centralizes policy.

Active vs passive health checks

  • Active (proactive): the balancer periodically probes a /health endpoint. Detects dead upstreams even with no traffic, but adds probe load and reacts only as fast as the probe interval.
  • Passive (reactive): the balancer infers health from real traffic — if an upstream returns errors or times out, eject it from the pool for a cool-down ("outlier detection"). Reacts instantly to real failures, but needs traffic to notice.

Production systems use both: passive ejection for fast reaction, active probing to decide when an ejected node is healthy enough to return. A good health check is deep enough to catch real problems (can it reach its own DB?) but not so deep that a downstream blip marks every node unhealthy at once and empties the pool.

    server 10.0.0.3:8080 backup;      # only used if the others are down
    keepalive 32;                     # reuse upstream connections
}

    location /api/ {
        proxy_pass http://api_backend;
        proxy_connect_timeout 1s;

Chapter 04

Asynchronous Communication & Queues

Synchronous calls couple the availability of caller and callee: if the callee is down, the caller fails. Message queues break that coupling — the producer hands work to a broker and moves on; the consumer processes it when able. But asynchrony introduces its own hard questions: did my message actually get delivered? Will the order be created twice? Can a payment be processed more than once? This chapter builds a reliable async pipeline: guaranteed delivery, deduplication, and seamless scaling.

4.1 Brokers: Kafka vs RabbitMQ

The two dominant models are the log (Kafka) and the queue (RabbitMQ). They are not interchangeable.

Buffering & load levelling

The first super-power of a queue is load levelling: it absorbs a spike. If a flash sale produces 50,000 orders/second but your fulfilment service handles 5,000/second, the queue buffers the difference and the consumers drain it steadily. The producer never overwhelms the consumer; the spike becomes a slightly longer backlog instead of an outage. The trade-off is latency — work is now processed eventually, not immediately — and you must monitor the backlog (consumer lag, Chapter 6).

Scaling under load

In Kafka, parallelism is bounded by partition count: a consumer group can have at most one consumer per partition actively reading. Add partitions to scale out — but choosing a partition key determines ordering and skew. Hash by order_id and all events for one order stay ordered on one partition; a hot key (one huge customer) creates a hot partition that one consumer can't keep up with.

4.2 Delivery Guarantees

There are three possible guarantees, and the names describe exactly what they promise:

GuaranteePromiseFailure mode
At-most-onceNever delivered twiceMay be lost (ack before processing)
At-least-onceNever lostMay be duplicated (ack after processing, crash in between)
Exactly-onceNever lost, never duplicatedExpensive; only within limited boundaries
"Exactly-once" is mostly a lie — and that's fine

True end-to-end exactly-once delivery is impossible over an unreliable network (it reduces to the two generals problem). What systems actually provide is at-least-once delivery + idempotent processing = effectively-once. Kafka's "exactly-once semantics" works only within Kafka (transactional reads-process-writes between Kafka topics); the moment you touch an external database or API, you're back to at-least-once + idempotency. So the real engineering goal is: at-least-once delivery, and make the consumer idempotent.

4.3 Distributed Transactions: SAGA vs 2PC

You can't wrap a database write and a message publish (or two services' databases) in a single ACID transaction across the network. Two patterns address this.

Two-Phase Commit (2PC)

A coordinator runs a prepare phase (every participant votes "ready" and locks resources) then a commit phase (everyone commits). It gives strong consistency but is blocking: if the coordinator crashes after prepare, participants hold locks indefinitely, and the whole transaction is unavailable. It scales poorly and couples availability of all participants — generally avoided in microservices.

The SAGA pattern

A SAGA breaks a distributed transaction into a sequence of local transactions, each with a compensating action that semantically undoes it. If step 4 fails, you run the compensations for steps 3, 2, 1 in reverse. There is no global lock and no isolation — instead you accept temporary inconsistency and design explicit "undo" logic.

2PCSAGA
ConsistencyStrong (atomic)Eventual
LocksHeld across the whole transactionOnly within each local step
AvailabilityBlocks on any participant/coordinator failureHigh; no global blocking
ComplexityIn the protocolIn your compensation logic

SAGAs come in two flavours: orchestration (a central coordinator tells each service what to do next — easier to reason about and monitor) and choreography (each service reacts to events and emits the next — more decoupled but harder to trace).

// Orchestrated SAGA: each step has a forward action and a compensation.
type Step struct {
    Do         func(ctx context.Context) error
    Compensate func(ctx context.Context) error
}

func RunSaga(ctx context.Context, steps []Step) error {
    var done []Step
    for _, s := range steps {
        if err := s.Do(ctx); err != nil {
            // Roll back everything already done, in reverse order.
            for i := len(done) - 1; i >= 0; i-- {
                // Compensations must be idempotent and retried until they succeed.
                _ = retryUntilSuccess(ctx, done[i].Compensate)
            }
            return fmt.Errorf("saga aborted: %w", err)
        }
        done = append(done, s)
    }
    return nil
}

4.4 Reliable Producing & the Outbox Pattern

Here is the bug that silently loses events in countless systems: a service commits a row to its database, then publishes a message to the broker as a second, separate step. If it crashes between those two steps, the database has the order but the broker never got the event — the rest of the system never finds out. This is the dual-write problem: two systems, no shared transaction.

You cannot fix the dual-write problem by reordering. Publish-then-commit can publish an event for a transaction that later rolls back (a phantom event). Commit-then-publish can lose the event on a crash. Either ordering is wrong. You need the outbox.

The transactional outbox

Write the message into an outbox table in the same local transaction as your business data. Now the order and the intent-to-publish commit atomically — they can't diverge. A separate relay process (a poller, or a change-data-capture stream like Debezium reading the WAL — §1.5) reads unpublished outbox rows and ships them to the broker, marking them sent. Delivery is at-least-once (the relay may crash after publishing, before marking), which is exactly why consumers must be idempotent (§4.5).

-- Step 1: business write + outbox row in ONE transaction (atomic).
BEGIN;
  INSERT INTO orders (id, user_id, total, status)
       VALUES ('ord_42', 'u_7', 1999, 'CREATED');
  INSERT INTO outbox (id, topic, payload, created_at)
       VALUES ('evt_99', 'orders.created',
               '{"orderId":"ord_42","total":1999}', now());
COMMIT;
// Step 2: a relay drains the outbox to the broker, at-least-once.
func (r *Relay) pump(ctx context.Context) error {
    rows, err := r.db.Query(ctx,
        `SELECT id, topic, payload FROM outbox
           WHERE published_at IS NULL
           ORDER BY created_at
           LIMIT 100
           FOR UPDATE SKIP LOCKED`) // SKIP LOCKED lets relays run in parallel
    if err != nil {
        return err
    }
    defer rows.Close()

    for rows.Next() {
        var id, topic string
        var payload []byte
        _ = rows.Scan(&id, &topic, &payload)

        if err := r.broker.Publish(ctx, topic, id, payload); err != nil {
            return err // leave it unpublished; retried next tick
        }
        _, _ = r.db.Exec(ctx,
            `UPDATE outbox SET published_at = now() WHERE id = $1`, id)
    }
    return nil
}

4.5 Reliable Consuming & the Inbox Pattern

Because delivery is at-least-once, the consumer is where correctness is enforced. Two concerns: when do you commit your progress, and how do you handle duplicates.

Offsets: manual vs auto commit

Kafka tracks consumer progress as an offset per partition. With auto-commit, the client periodically commits the latest read offset in the background — convenient, but it can commit an offset for a message you haven't finished processing, so a crash loses it (at-most-once). With manual commit, you commit only after successfully processing — a crash before commit means redelivery (at-least-once). Manual commit, after processing, is the durable choice.

Process, then commit — never the reverse. Commit-after-processing gives at-least-once (safe with idempotency). Commit-before-processing gives at-most-once (silent data loss on crash). The ordering of these two lines is one of the most consequential decisions in a consumer.

The inbox pattern (idempotent consumer)

To process each message effectively once despite redelivery, record every processed message's ID in an inbox table, and check it before acting — atomically, in the same transaction as the side effect. A duplicate finds its ID already present and is skipped.

// Idempotent consumer: dedupe via an inbox table, commit offset after.
func (c *Consumer) handle(ctx context.Context, msg Message) error {
    tx, err := c.db.Begin(ctx)
    if err != nil {
        return err
    }
    defer tx.Rollback(ctx)

    // Claim the message id. If it's already there, this is a duplicate.
    tag, err := tx.Exec(ctx,
        `INSERT INTO inbox (message_id, processed_at)
              VALUES ($1, now())
         ON CONFLICT (message_id) DO NOTHING`, msg.ID)
    if err != nil {
        return err
    }
    if tag.RowsAffected() == 0 {
        return c.commitOffset(ctx, msg) // duplicate: ack and move on
    }

    // First time: do the side effect in the SAME transaction as the inbox row.
    if err := c.applyBusinessLogic(ctx, tx, msg); err != nil {
        return err // rollback drops the inbox row too -> safe to redeliver
    }
    if err := tx.Commit(ctx); err != nil {
        return err
    }
    return c.commitOffset(ctx, msg) // only after the work is durable
}
Outbox + Inbox = end-to-end effectively-once

The outbox guarantees the event is never lost on the producer side; the inbox guarantees it is never applied twice on the consumer side. Together, over an at-least-once broker, they deliver the "exactly-once" behaviour the business actually wants — without any distributed transaction. This pairing is the backbone of reliable event-driven systems.

4.6 Dead Letter Queues

Some messages can never be processed: malformed payloads, references to deleted entities, a bug that throws on a specific shape of data. These are poison messages. If you simply retry them forever, the consumer is stuck — it redelivers the poison message, fails, redelivers it, and the partition's backlog grows behind it (head-of-line blocking).

The solution is a Dead Letter Queue (DLQ): after N failed attempts, move the message to a separate queue and continue with the next message. The DLQ becomes a quarantine you can inspect, alert on, fix, and replay from.

// Route a message to the DLQ after exhausting retries; never block the stream.
func (c *Consumer) process(ctx context.Context, msg Message) {
    err := retryWithBackoff(ctx, func() error {
        return c.handle(ctx, msg)
    })
    if err == nil {
        return
    }
    if attempts(msg) >= c.maxAttempts {
        // Quarantine with full context for the on-call engineer.
        c.dlq.Publish(ctx, DeadLetter{
            Original:    msg,
            Error:       err.Error(),
            Attempts:    attempts(msg),
            FailedAt:    time.Now(),
            ConsumerVer: c.version,
        })
        c.commitOffset(ctx, msg) // unblock the partition
        c.metrics.DLQ.Inc()      // ALERT on this — a rising DLQ is a real incident
        return
    }
    // else: let it be redelivered with an incremented attempt count
}
A DLQ is not a dustbin. Messages landing in it represent lost business events — an order not fulfilled, a payment not recorded. The DLQ must be monitored and alerted on (Chapter 6), have a documented replay procedure, and ideally a retention long enough to fix the bug and reprocess. An unwatched DLQ is just slow, silent data loss.

  • Aim for at-least-once delivery + idempotent processing = "effectively once"; true exactly-once is a near-myth

Chapter 05

The Caching Layer in High-Availability Systems

You add a cache to make the system faster — and accidentally invent a whole new family of outages. The cache expires and a flood of identical requests stampedes your database. Users see data that's minutes stale and file bug reports. A thousand keys expire at the same second and the origin falls over. Caching is a power tool with sharp edges; this chapter is the safety manual.

5.1 Stale Data, TTL & Invalidation

"There are only two hard things in computer science: cache invalidation and naming things." The fundamental tension of a cache is that it holds a copy, and copies drift from the source of truth. Three mechanisms keep them in line:

  • TTL (time to live) — every entry expires after a fixed duration. Simple, self-healing, and bounds staleness to at most the TTL. The downside: data can be stale for up to the full TTL, and everything written at once expires at once (see §5.4).
  • Active (write) invalidation — when the underlying data changes, explicitly delete or update the cache entry. Fresh, but you must find every write path, and it's racy (§5.2).
  • Event-driven invalidation — the source of truth emits a change event (e.g. via the outbox / CDC of §4.4) and cache nodes invalidate on it. Scales to many cache instances and decouples writers from caches.

5.2 Cache Consistency

The naïve cache-aside write — "update the DB, then delete the cache key" — has a famous race. Consider a concurrent reader and writer:

// The classic cache-aside race (read fills a STALE value):
//   T1 (read):  cache miss for key K
//   T1 (read):  SELECT from DB -> gets OLD value v0
//   T2 (write): UPDATE DB -> v1
//   T2 (write): DELETE cache key K        (nothing there yet)
//   T1 (read):  SET cache K = v0          (writes the STALE value!)
//   => cache now serves v0 until TTL, even though DB holds v1.

Mitigations, roughly in order of strength:

  • Delete, don't update the cache on writes — next read repopulates from the DB. Updating in place invites lost-update races.
  • Delayed double delete — delete the key, write the DB, then delete again after a short delay to evict any stale value a concurrent read slipped in.
  • Versioning / CAS — store a version with each value and only overwrite if the version is newer.
  • Short TTL as a backstop — even if invalidation races, the TTL bounds how long a stale value can survive.

Compare-and-swap (check-and-set)

CAS lets you update a value only if it hasn't changed since you read it — the atomic primitive behind optimistic concurrency. Redis exposes it via WATCH/MULTI/EXEC (and memcached via gets/cas). It turns "read-modify-write" into a safe operation even with concurrent writers: if someone changed the key under you, the transaction aborts and you retry.

// Optimistic update with Redis WATCH (compare-and-swap).
func incrementCounter(ctx context.Context, rdb *redis.Client, key string) error {
    return rdb.Watch(ctx, func(tx *redis.Tx) error {
        n, err := tx.Get(ctx, key).Int()
        if err != nil && err != redis.Nil {
            return err
        }
        // EXEC fails (and Watch retries) if `key` changed since WATCH.
        _, err = tx.TxPipelined(ctx, func(p redis.Pipeliner) error {
            p.Set(ctx, key, n+1, 0)
            return nil
        })
        return err
    }, key)
}
Replication in the cache tier

Redis can replicate to read replicas and fail over via Sentinel or Cluster, but replication is asynchronous: a read replica may lag the primary, so a read-after-write against a replica can return the old value. And on failover, writes acknowledged by the primary but not yet replicated are lost. Treat the cache as best-effort, never as the source of truth — the database (Chapter 1) is.

5.3 Thundering Herd

A popular key expires. In the same millisecond, a thousand concurrent requests miss the cache and all rush to the database to recompute the same value. The database, sized for cache-hit traffic, buckles. This is the thundering herd (or cache stampede), and it's the most common cache-induced outage.

Defenses:

  • Single flight (request coalescing) — §3.3 applied to cache fills: let exactly one request recompute the value while the rest wait for and share its result.
  • Soft TTL + background refresh — store a "soft" expiry before the hard one. When a read finds the value past its soft TTL, it serves the still-valid value and triggers an async refresh — readers never block on a recompute.
  • Distributed lock — the first miss takes a short-lived lock (e.g. Redis SET key val NX PX); others briefly serve stale or wait. Simpler across many app instances than in-process single flight, but watch lock expiry.
// Stampede protection with single flight + soft-TTL background refresh.
func (c *Cache) Get(ctx context.Context, key string) ([]byte, error) {
    v, ok := c.store.Get(key)
    if ok && time.Now().Before(v.softExpiry) {
        return v.data, nil // fresh enough
    }
    if ok {
        // Past SOFT ttl but still within HARD ttl: serve stale, refresh async.
        go c.refresh(context.WithoutCancel(ctx), key)
        return v.data, nil // nobody blocks; no herd
    }
    // Hard miss: collapse all concurrent misses into ONE origin call.
    data, err, _ := c.sf.Do(key, func() (interface{}, error) {
        return c.loadFromOrigin(ctx, key)
    })
    if err != nil {
        return nil, err
    }
    return data.([]byte), nil
}

5.4 Cache Avalanche & Penetration

Cache avalanche

A cache avalanche is the thundering herd at scale: a large set of keys expires simultaneously (e.g. you warmed 100k keys at deploy with the same TTL), or the cache layer itself restarts and comes up empty. The origin is hit by a wall of misses across many keys at once. Defenses:

  • Random TTL / jitter — add a random spread to each TTL (ttl ± rand(0, 10%)) so keys expire at different times instead of in lockstep. This is the single most important avalanche defense, and it's one line of code.
  • Multi-level caching — a small in-process L1 cache in front of the shared L2 (Redis) absorbs hot keys and survives an L2 restart.
  • Proactive refresh — warm/refresh hot keys before they expire, on a schedule.
  • Origin rate limiting — cap concurrent origin loads (bulkhead, §3.1) so even a full avalanche can't overwhelm the database — excess requests serve stale or fail fast.

Cache penetration

Cache penetration is the inverse: requests for keys that don't exist (often malicious — random non-existent IDs). They always miss the cache and always hit the database, since there's nothing to cache. Defenses: cache the negative result (store a short-TTL "not found" sentinel) and/or front the cache with a Bloom filter of existing keys to reject impossible lookups in O(1) before they touch the DB.

Three "cache disasters", three fixes. Penetration = key never exists → cache negatives + Bloom filter. Thundering herd = one hot key expires → single flight + soft TTL. Avalanche = many keys expire together → random TTL jitter + multi-level cache. Knowing which is which under fire is half the battle.

5.5 Eviction Strategies

A cache has finite memory; when it's full, it must evict something to admit a new entry. The policy determines your hit rate.

PolicyEvictsGood when
LRU — Least Recently UsedThe entry untouched longestRecency predicts reuse (most workloads). The default.
LFU — Least Frequently UsedThe entry accessed fewest timesA stable hot set; resists one-off scans polluting the cache
FIFO — First In First OutThe oldest inserted entryRarely ideal; ignores access pattern
MRU — Most Recently UsedThe entry touched most recentlyLooping scans over a dataset larger than the cache
RandomA random entryCheap, no metadata; surprisingly decent, used by Redis (approx-LRU/LFU)
LRU's blind spot: a large sequential scan (a batch job touching millions of rows once) evicts your entire hot set even though those scanned entries will never be read again. LFU and "scan-resistant" variants (like the W-TinyLFU used in Caffeine) defend against this. Modern caches often blend recency and frequency rather than picking one. 
// O(1) LRU: a hash map for lookup + a doubly linked list for recency order.
type LRU struct {
    cap   int
    items map[string]*list.Element // key -> node
    order *list.List               // front = most recent, back = least
}

func (c *LRU) Get(key string) (any, bool) {
    if el, ok := c.items[key]; ok {
        c.order.MoveToFront(el)    // mark as most-recently-used
        return el.Value.(*entry).val, true
    }
    return nil, false
}

func (c *LRU) Put(key string, val any) {
    if el, ok := c.items[key]; ok {
        el.Value.(*entry).val = val
        c.order.MoveToFront(el)
        return
    }
    if c.order.Len() >= c.cap {    // full: evict the least-recently-used
        back := c.order.Back()
        c.order.Remove(back)
        delete(c.items, back.Value.(*entry).key)
    }
    c.items[key] = c.order.PushFront(&entry{key, val})
}
Metrics that tell you the cache is healthy

Watch hit ratio (a sudden drop signals an invalidation storm or avalanche), eviction rate (high → cache too small for the working set), origin load / miss latency (the thing the cache is supposed to protect), and key TTL distribution (clustered expiries → avalanche risk). A cache you can't observe is a cache that will surprise you (Chapter 6).

Key Takeaways — Chapter 5
  • TTL bounds staleness automatically; active/event invalidation is fresher but racy and must cover every write path
  • On writes, delete the key rather than update it; use CAS/versioning for safe concurrent updates
  • The cache is best-effort and async-replicated — never the source of truth
  • Thundering herd (one hot key) → single flight + soft-TTL background refresh
  • Avalanche (many keys at once) → random TTL jitter + multi-level cache; penetration → cache negatives + Bloom filter
  • LRU is the sensible default; LFU/scan-resistant policies defend against scan pollution
Chapter 06

Failure Detection & Response

You put out one fire and the next is already burning. Users hit errors before your alerts fire. That's the default state of a system without good observability and a practiced response process. This final chapter is about seeing failure before it reaches the user, localizing it fast across synchronous and asynchronous paths, and responding when automation has run out of answers.

6.1 Incident Management & Observability

Detection rests on the three pillars of observability, and resilient teams use them in a deliberate order:

PillarAnswersUse for
Metrics"Is something wrong, and how bad?"Dashboards, alerting, SLOs — cheap, aggregate
Traces"Where in the call graph is the latency/error?"Localizing across services (distributed tracing)
Logs"What exactly happened to this request?"Root-cause detail once you've localized

Metrics tell you that something broke; traces tell you where; logs tell you why. Alerting on metrics, drilling with traces, and confirming with logs is the fast path from page to fix.

The coordinator (incident commander)

When an incident spans teams, someone must own the response. The coordinator (or incident commander) does not personally fix everything — they centralize the response: maintain the single source of truth on status, delegate investigation, decide on mitigations (roll back? shed load? fail over?), and shield the responders from the flood of "is it fixed yet?" The role exists so that five engineers don't independently make five conflicting changes during an outage.

Business metrics are the real SLO

CPU and memory can look perfectly healthy while the business is on fire. The metrics that matter most are business-level: orders per minute, successful payments, login success rate, messages delivered. A drop in "checkouts per minute" detects a broken checkout that no infrastructure metric would reveal. Alert on the symptom the user feels (orders falling), then use technical metrics to find the cause.

Planned work & communication

A surprising share of incidents are self-inflicted: maintenance windows, migrations, certificate rotations, dependency upgrades. The discipline that prevents these from becoming outages is communication — announce planned work, its blast radius, and its rollback plan before it happens, so that when latency blips, on-call knows it's the migration and not a new fire. And when automation (auto-scaling, auto-failover, circuit breakers) doesn't save you, you need a documented manual runbook (§6.5) and the authority to execute it.

6.2 Monitoring Synchronous Calls

For request/response services, Google's Four Golden Signals are the canonical starting set:

SignalWhat to watchWhy
Latencyp50 / p95 / p99 / p99.9 — split success vs error latencyTail latency is where users hurt; averages hide it
TrafficRequests/sec, by endpointContext for the other signals; detects spikes/drops
ErrorsRate of 5xx, timeouts, by codeThe most direct symptom; powers SLO burn alerts
SaturationCPU, memory, connection pools, queue depthHow close to the limit — predicts imminent failure
Always measure percentiles, never just the average. A mean latency of 50 ms can hide a p99 of 5 s — meaning 1% of users (often your biggest, most active ones) are having a terrible time. And never average percentiles across instances — p99 of p99s is mathematically meaningless. Aggregate the raw histograms.

Beyond the golden signals: watch resource utilization against limits (a connection pool at 95% is a cascade waiting to happen — §3.1), and the health of your dependencies — your database, the third-party APIs you call, the cache. Their saturation becomes your latency. Rich, structured, correlatable logs (a trace/request ID on every line) are what turn "the service is slow" into "this specific query against this shard is slow." And alerts must be actionable: an alert that fires without a clear response just trains people to ignore alerts (§6.4).

6.3 Monitoring Asynchronous Pipelines

Async systems fail differently. There's no failed HTTP response to count — a broken consumer manifests as work silently not getting done. The master signal is consumer lag.

Consumer lag

Lag = (latest offset produced) − (latest offset committed by the consumer group), per partition. It's the number of messages waiting to be processed. A small, stable lag is healthy. A steadily growing lag means consumers can't keep up with producers — the backlog will grow without bound and processing latency with it. This is the async equivalent of saturation.

Async metricSignals
Consumer lag (per partition)Are we keeping up? Growing lag = under-provisioned or stuck
Processing rate & timeThroughput and per-message cost; a spike in time → a slow dependency
Partition skewOne partition lagging while others are fine → a hot key (§4.1) or a poison message (§4.6)
Consumer group stateFrequent rebalances stop all consumption; a stuck member blocks its partitions
DLQ size / rateMessages being abandoned — direct business-event loss
End-to-end latencyproduce-time → process-time; what the downstream actually experiences
Rebalancing storms. When a consumer joins, leaves, or is presumed dead (missed heartbeat), the group rebalances — and during the stop-the-world phase of a rebalance, the whole group pauses consumption. A consumer that's slow to process can miss its max.poll.interval, get kicked, trigger a rebalance, and make the lag worse — a feedback loop. Tune poll intervals and session timeouts to the real processing time.

6.4 Alerting & On-Call

Alerts are the bridge between detection and response. Bad alerting is worse than none: it causes alert fatigue, where so many false or non-actionable alerts fire that responders start ignoring them — and miss the real one. Principles for alerts that shorten time-to-recovery rather than lengthen it:

  • Alert on symptoms, not causes. Page on "checkout error rate > 1%" (what the user feels), not on "CPU > 80%" (which may be fine). One symptom alert replaces dozens of noisy cause alerts.
  • Every page must be actionable. If there's nothing to do, it shouldn't page — make it a ticket or a dashboard. A page means "a human must act now."
  • Use SLO burn-rate alerts. Page fast when you're burning the error budget quickly (a sharp outage), and more gently for slow burns. This ties alerting directly to user impact (§1.3).
  • Multi-window, multi-burn-rate reduces false positives: require both a short window (fast detection) and a longer one (confirmation) to fire.
# Prometheus-style multi-burn-rate SLO alert (99.9% objective).
# Fast burn: 2% of the 30-day budget in 1h -> page immediately.
- alert: CheckoutErrorBudgetFastBurn
  expr: |
    (
      sum(rate(http_requests_total{job="checkout",code=~"5.."}[5m]))
      / sum(rate(http_requests_total{job="checkout"}[5m]))
    ) > (14.4 * 0.001)        # 14.4x burn rate vs the 0.1% budget
    and
    (
      sum(rate(http_requests_total{job="checkout",code=~"5.."}[1h]))
      / sum(rate(http_requests_total{job="checkout"}[1h]))
    ) > (14.4 * 0.001)        # confirm over a longer window
  for: 2m
  labels: { severity: page }
  annotations:
    summary: "Checkout burning error budget 14.4x — user-facing outage"
    runbook: "https://runbooks/checkout-5xx"
Every alert links to a runbook. A page at 3 a.m. is not the time to reverse-engineer the system. The runbook says: what this alert means, how to confirm it's real, the first three mitigations to try (roll back? shed load? fail over?), and who to escalate to. Runbooks turn heroics into procedure.

6.5 Manual Recovery

Sometimes automation isn't enough and you have to operate on the system by hand. For async systems, the most common manual interventions involve offsets and consumer groups — powerful, and dangerous if done carelessly.

SituationManual interventionRisk
Poison message wedged a consumer (no DLQ)Skip it: commit offset past the bad messageSkips a real event — record what you skipped
A bug processed messages wronglyReset offsets back and reprocessRe-delivers — only safe if consumers are idempotent (§4.5)
Unrecoverable backlog after an outageScale consumers / add partitions; or skip to latest if data is disposableSkipping to latest abandons the backlog
Stuck/zombie consumer holding partitionsForce it out of the group; let rebalance reassignTriggers a rebalance (brief pause, §6.3)
# Reset a consumer group to reprocess the last hour (idempotent consumers only!).
# 1. STOP the consumer group first — you cannot reset offsets while it's active.
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --group orders-processor \
  --topic orders.created \
  --reset-offsets --to-datetime 2026-06-14T09:00:00.000 \
  --dry-run            # ALWAYS dry-run first to see the planned moves

# 2. Inspect, then re-run with --execute when satisfied.
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --group orders-processor --topic orders.created \
  --reset-offsets --to-datetime 2026-06-14T09:00:00.000 --execute

# Check current lag at any time:
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --group orders-processor --describe   # shows LAG per partition
Resetting offsets without idempotent consumers means reprocessing side effects — re-charging cards, re-sending emails, double-creating orders. This is precisely why Chapter 4 insisted on the inbox pattern: it makes manual replay safe. The resilience you build in calm times is what gives you safe options during an incident.

After the incident: the blameless post-mortem

The course material asks, half-jokingly, "how do we punish the guilty?" The mature answer is: we don't. The goal of a post-mortem is to fix the system, not the person — because a system where one human's mistake causes an outage is a system with a missing safeguard (recall GitLab, §1.6: the problem wasn't the engineer who ran rm -rf, it was the five backups that had silently failed). A blameless post-mortem documents the timeline, the contributing factors, what went well, and concrete action items — so the same failure can't recur. Blame makes people hide mistakes; blamelessness makes them surface the weak spots you most need to know about.

Closing the loop

Resilience is a cycle, not a checklist. You design for failure (Chapters 1–5), you detect it fast (this chapter), you respond with practiced procedures, and you learn via blameless post-mortems that feed new safeguards back into the design. The systems that stay up aren't the ones that never fail — they're the ones that fail in small, contained, well-understood ways, and get a little harder to break after every incident.
